## Why

Users need a lightweight way to track direct account-to-account expenses with one other person, without the ceremony of creating a named multi-person group. A previous attempt at a full "direct ledger" refactor introduced a parallel ledger/group/type system and proved too complex. Instead, this change piggy-backs on the existing group implementation: a friend expense ledger is just a group with a `FRIEND` type discriminator and a few server-enforced constraints, so all existing expense, split, balance, invitation, and activity machinery is reused unchanged.

Renaming the existing "contacts" concept to "friends" makes the vocabulary consistent: "friend contacts" are people you have shared groups with, and a "friend expense" ledger is the 1-on-1 ledger between you and one of them.

This change also cleans up `AccountGroupPreference`: the per-account `archived` column (which was already being exposed on the API surface as `hidden`) is merged into the existing `hidden` column, and the dormant `pinned` column (selected by the API but never read or toggled anywhere in the app) is dropped. The existing `starred` column stays as-is and continues to back the "Starred" homepage section — no rename, no behavior change. The group-level `Group.archived` flag remains unchanged.

## What Changes

- Add a `GroupType` enum (`GROUP`, `FRIEND`) and a `groupType` column on `Group` defaulting to `GROUP`. All existing groups become `GROUP`.
- Add a `FriendLink` junction table (with `accountAId`/`accountBId` using a smaller-id-first convention, `groupId`, and `@@unique([accountAId, accountBId])`) so that at most one `FRIEND` group exists per unordered account pair. `Account` gains `friendLinksAsA`/`friendLinksAsB` relations, similar to `groupMemberships`. The create flow is lookup-or-create: if a friend ledger between the caller and the peer already exists, return it instead of creating a new one.
- Introduce a new `friends.create` API flow with two paths. **Direct-accept path:** when the peer can be resolved to a known `accountId` — either picked from the friends list OR entered by email that belongs to an existing `Account` — the friend group is created with both accounts as ACTIVE `ADMIN` members immediately, no invitation step, the ledger appears on both sides on next load. **Pending path:** when the peer cannot be resolved to an `accountId` (email without an account, or link invite), the caller becomes ADMIN immediately and a `PENDING` invitation is created for the peer; this invitation is **auto-accepted** (no user-facing Accept/Decline) when the peer's account becomes available — on signup with a matching email, or on opening the link. The optional `temporaryName` already supported by `GroupInvitation` is the display name while the invitation is pending. Friend invitations do not appear in the homepage's Pending Invitations card.
- Set the friend group's `name` column to an empty string at create time (the simplest possible value; never shown to users). The display name shown to each viewer is computed per-viewer as the OTHER member's display name, using the existing `resolveParticipantDisplayName` priority chain (`Account.name` → `Invitation.temporaryName` → `Invitation.email`).
- For `FRIEND` groups, server-enforce the following by branching on `groupType`: both members are created as `ADMIN`; rename (name change only), delete, archive/unarchive, leave, creating additional invitations, and revoking pending invitations are rejected with a clear error. Currency and information remain editable (same settings flow as regular groups). Star and hide remain available to each member independently. The group-level `Group.archived` flag is never set on a `FRIEND` group.
- Rename the existing "contacts" concept to "friends" throughout: the `account.contacts` query becomes `account.friends` (enriched with "friend ledger already exists" metadata for each contact), the "Contacts" tab in the invite UI becomes "Friends", and all related copy, types, and translation keys are updated. The semantics are unchanged — the list is still computed on the fly from shared group memberships.
- Collapse `AccountGroupPreference` to two live columns: merge the per-account `archived` column into the existing `hidden` column (`hidden = hidden OR archived`), then drop `archived`; drop the dormant `pinned` column outright (it is never read or toggled). The API surface changes from `preference: { starred, hidden, pinned }` to `preference: { starred, hidden }`, and `setPreference` no longer accepts a `pinned` input.
- Reshape the signed-in homepage into separate sections: **Starred** (unchanged name; mixed groups and friend ledgers), **Groups** (replaces "Recent"; all active non-starred, non-archived, non-hidden groups), **Friends** (all non-starred, non-hidden friend ledgers, even if fully settled), **Archived** (regular groups only, since archive is not a friend-ledger concept), and **Hidden** (toggled via "Show hidden"; mixed groups and friend ledgers). Pending invitations remain at the top.
- Add section-level "Create expense" buttons on the homepage — one next to the "Groups" section heading and one next to the "Friends" section heading. Each button opens a `ResponsiveDialog` scope-picker listing only that section's items (groups or friends). Selecting an item navigates to the existing full-page create-expense form. No per-card "Create expense" buttons. When the user is already inside a group or friend ledger, the existing direct navigation is unchanged.
- Add a dedicated `/friends/create` web route with a bespoke form: a friends/email/link picker for the peer, a currency selector (reusing the existing `CurrencySelector`), an optional info textarea (friends may want to add context), and an optional temporary name field used only when inviting by email or link. On the link path, the user is navigated to the group page immediately and the invite link is shown in a `ResponsiveDialog` on the group page itself. The regular `/groups/create` route is left untouched for multi-person groups.

## Capabilities

### New Capabilities

- `friends`: 1-on-1 account-to-account expense ledgers represented as a `FRIEND`-typed group, with per-pair uniqueness, both-admin membership, restricted action set, server-derived name, and per-viewer display name resolution.

### Modified Capabilities

- `groups`: `Group` gains a `groupType` discriminator; create/list/get procedures carry the type and, for `FRIEND`, enforce restricted actions (no rename, delete, archive, leave, additional invitations, or invitation revocation — but currency and information remain editable) and surface a per-viewer `displayName`. The public `invitations.previewLink` shows a FRIEND-aware display name instead of `Group.name`.
- `group-membership`: friend ledgers create both members as `ADMIN` simultaneously when the peer is a known account (contact or email-with-existing-account); leaving a friend ledger is rejected; pending invitations (email without account, link) are auto-accepted when the peer's account becomes available — no user-facing accept/deny.
- `account-profiles`: the "contacts" concept is renamed to "friends" (query, UI, types, copy); per-account group preferences collapse from `{ starred, hidden, pinned }` to `{ starred, hidden }` by dropping the dormant `pinned` column and merging the per-account `archived` column into `hidden`.

## Impact

- Database: new `GroupType` enum and `Group.groupType` column with a default and backfill migration; new `FriendLink` junction table with `accountAId`/`accountBId` (smaller-id-first convention), `groupId` (`@unique`), and `@@unique([accountAId, accountBId])`; `Account` gains `friendLinksAsA`/`friendLinksAsB` relations; `Group` gains a `friendLink` relation (nullable); `AccountGroupPreference` migration to merge the per-account `archived` column into `hidden` then drop `archived`, and to drop the dormant `pinned` column outright.
- API: new `friends.create` procedure (direct-accept path for contacts and emails-with-accounts, pending path for emails-without-accounts and links, lookup-or-create via `FriendLink`); `groups.create` does NOT gain a `groupType` input (all friend ledgers created via `friends.create` only); `account.groups` returns `groupType` and a resolved `displayName`; group mutation procedures (archive, update name field, delete, leave, invitation create, invitation revoke) branch on `groupType` and reject `FRIEND` where applicable (`groups.update` for `FRIEND` allows `information` and `currency` changes, rejects `name`); `invitations.previewLink` returns a FRIEND-aware display name; auto-accept hook for friend invitations on signup and link-open; friend invitations filtered out of `invitations.listForAccount`; `account.contacts` is renamed to `account.friends` and enriched with friend-ledger-exists metadata; `account.preferences` and `account.setPreference` drop `pinned`.
- Web: new `/friends/create` route with a peer-picker form (including optional info textarea); `GroupCard` renders the resolved `displayName` for friend ledgers, shows the peer's avatar (initials fallback), shows a subtle "Pending" badge for pending friend ledgers, and hides the archive action for `FRIEND` groups; the group detail page hides the Members tab for `FRIEND` groups and shows the Settings tab with the name field disabled but currency/information editable; homepage splits into separate "Groups" and "Friends" sections (drops "Recent"), keeps "Starred" mixed, keeps "Archived" groups-only, keeps "Hidden" mixed; section-level "Create expense" buttons open a `ResponsiveDialog` scope-picker (one for Groups, one for Friends); link-path submit navigates to the group page with a `ResponsiveDialog` showing the invite link; "Contacts" tab and copy become "Friends" across the invite UI and anywhere else the term appears.
- Domain: a new `friendFormSchema` is introduced for the peer-picker + currency + info + temporary-name inputs; expense and split schemas are reused unchanged.
- Translations: `en-US.json` is the source of truth and must be updated via the `bun i18n` CLI (never hand-edited) to rename "contacts"/"Contacts" to "friends"/"Friends", rename "recent"/"Recent" to "groups"/"Groups" where it refers to the homepage section, and add any new friend-ledger copy; other locales follow via the translate-strings skill. No "starred"/"pinned" rename is needed.
- Testing: API integration tests for `friends.create` (direct-accept with contact, direct-accept with email-that-has-account, pending with email-without-account, link path, lookup-or-create idempotency, both-admin membership, per-pair uniqueness); auto-accept tests (signup triggers auto-accept, link-open triggers auto-accept); server-enforcement tests for the restricted `FRIEND` actions (rename blocked, currency/information allowed, archive/delete/leave/invite/revoke blocked); `previewLink` FRIEND-aware display name test; web tests for the homepage section splitting (Groups vs Friends), the friend card rendering (displayName, avatar, pending badge), the section-level "Create expense" scope-picker dialogs, and the link-path dialog; migration test verifying per-account `archived`→`hidden` data preservation and that dropping `pinned` loses no live data.
- Invariants: at most one `FRIEND` group per unordered account pair (enforced by `FriendLink` unique constraint); `FRIEND` groups never have `Group.archived = true`; `FRIEND` groups always have exactly two ACTIVE members, both with role `ADMIN` (once any pending invitation is auto-accepted).
